Calibri enforces rate limits across all API surfaces to ensure fair access and platform stability. Public endpoints are protected by Cloudflare's IP-based throttling, while authenticated trading endpoints use per-signer token-bucket limits tied to your account tier. Understanding these limits — and designing your integration around them — will help you avoid disruptions in production.

## Public Endpoint Limits

Public endpoints (such as `GET /markets` and `GET /markets/{id}/prices-history`) are rate-limited at the network edge by **Cloudflare IP-based throttling**. Calibri does not publish a fixed request-per-minute ceiling for these endpoints, as limits are applied dynamically based on traffic patterns.

<Tip>
  Cache market metadata and price history responses on your end wherever possible. Market metadata rarely changes, and fetching it repeatedly from the same IP will increase your exposure to edge throttling.
</Tip>

## Authenticated Endpoint Limits

Trading and order-management endpoints on the CLOB API (`https://clob.calibri.com`) use a **per-signer token-bucket** model. Each signer address has its own bucket that refills at a rate determined by your account tier. This applies specifically to order placement and cancellation requests.

When your bucket is empty, the API returns `429 Too Many Requests` until the bucket refills.

## Account Tiers

Your account tier determines three key limits. You can retrieve your current limits at any time by calling `GET https://clob.calibri.com/account-limits`, which returns:

```json
{
  "actions_per_minute": 100,
  "open_orders": 50,
  "messages_per_minute": 200
}
```

| Limit Type | Description |
|------------|-------------|
| `actions_per_minute` | Total order actions (placements + cancellations) allowed per minute |
| `open_orders` | Maximum number of concurrently open orders on the book |
| `messages_per_minute` | Total API messages (requests) allowed per minute across all CLOB endpoints |

To see all available tier definitions and their thresholds, call:

```http
GET https://clob.calibri.com/limit-tiers
```

Tier promotions are **volume-based** — Calibri automatically evaluates your trading volume and upgrades your tier accordingly. If you need a higher tier for a specific integration or market-making program, contact Calibri support directly.

## Batch Limits

Several endpoints accept batched payloads to reduce the number of requests you need to make. Each has a hard cap on how many items you can include per request:

| Endpoint | Limit |
|----------|-------|
| `POST /orders` — batch order placement | Max **15 orders** per request |
| `DELETE /orders` — batch order cancellation | Max **1,000 order IDs** per request |
| `GET /last-trade-prices` — bulk last-trade prices | Max **500 token IDs** per request |

Exceeding these limits returns a `400 Bad Request` response — the entire batch is rejected, not partially processed.

## Handling 429 Too Many Requests

When you receive a `429` response, your request was not processed. The response body will contain an `error` field explaining the limit that was hit.

```json
{
  "error": "rate limit exceeded: actions_per_minute"
}
```

<Warning>
  Do not retry immediately after a `429`. Implement **exponential backoff with jitter** — start with a short delay (e.g. 500 ms), double it on each subsequent retry, and add random jitter to avoid thundering-herd collisions when multiple instances retry at the same time.
</Warning>

A safe retry strategy in pseudocode:

```typescript
async function withRetry(fn: () => Promise<Response>, maxAttempts = 5) {
  for (let attempt = 0; attempt < maxAttempts; attempt++) {
    const response = await fn();
    if (response.status !== 429) return response;

    const baseDelay = 500 * Math.pow(2, attempt);
    const jitter = Math.random() * 200;
    await sleep(baseDelay + jitter);
  }
  throw new Error("Max retry attempts exceeded");
}
```

## Best Practices

<AccordionGroup>
  <Accordion title="Use batch endpoints">
    Whenever you need to place or cancel multiple orders, use `POST /orders` and `DELETE /orders` in batch mode rather than making individual requests. A single batch call of 15 orders costs you one action against your `actions_per_minute` bucket instead of fifteen. This is the single most impactful change you can make to stay within your tier limits at scale.
  </Accordion>

  <Accordion title="Cache market metadata">
    Market metadata — including outcome labels, token IDs, resolution sources, and minimum tick sizes — changes infrequently. Instead of fetching `GET /markets/{id}` on every request, cache the response locally and refresh it periodically (e.g., every 5–10 minutes). This dramatically reduces your load on public endpoints and keeps your integration well under Cloudflare's edge limits.
  </Accordion>

  <Accordion title="Use WebSocket for real-time data">
    If your application needs live price or orderbook updates, subscribe to the WebSocket stream at `wss://ws-subscriptions-clob.calibri.com/ws/` instead of polling `GET /markets/{id}` or `GET /last-trade-prices` in a loop. Polling at high frequency is the most common cause of hitting rate limits on public endpoints. A single WebSocket connection delivers updates as they happen with no polling overhead.
  </Accordion>

  <Accordion title="Monitor your tier proactively">
    Call `GET https://clob.calibri.com/account-limits` at application startup and log your current `actions_per_minute`, `open_orders`, and `messages_per_minute` values. Build alerting around these limits before you hit them in production — don't wait for a `429` to tell you that your tier is too low for your traffic.
  </Accordion>
</AccordionGroup>
